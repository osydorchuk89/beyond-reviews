# Client accessibility: WCAG 2.2 AA

Make new and changed UI usable with a keyboard, assistive technology, enlarged text, and narrow screens. Apply the relevant A/AA criteria to the changed feature and its complete interaction. This is implementation guidance, not a conformance certificate or a request to audit unrelated pages.

## Work within this app

- Inspect the affected components and their callers before editing. Reuse existing React Router, React Hook Form/Zod, Headless UI, Tailwind, and Zustand patterns. Prefer native HTML controls to new ARIA widgets.
- Preserve the current appearance and the user's approved design. Semantics and behavior can usually improve without redesign. For a needed visual change outside existing authorization, prepare a concrete proposal/preview and obtain approval before applying it; continue independent work. Record any accessibility gap that remains rather than treating the design constraint as an exemption.
- Keep rating stars visually styled as stars: retain native radio semantics and keyboard operation without exposing radio circles. Show keyboard focus with the existing `:focus-visible` styles; do not reintroduce a mouse-click outline on stars or thicker custom outlines on text inputs. Do not restore the rejected pagination underline or bookmark checkmark without fresh authorization; preserve the approved light/dark selection treatments.
- Preserve the existing non-messaging fixes. Messaging remediation is deferred until its refactor; do not expand an unrelated task into that work. Apply this guidance when messaging UI itself is requested or refactored. Deferral does not mean that messaging meets WCAG.
- Existing registration password/photo instructions are screen-reader-only and remain a known gap. Do not copy that limitation into new forms: supply needed visible instructions within the approved design.

## Preserve the established behavior

| Area | Existing pattern and invariant |
| --- | --- |
| Page structure | Keep `MainLayout`, its single main landmark, and the skip link. Give each page a meaningful primary heading. Register route titles through route handles and preserve `PageNavigation` title/focus handling. `tabIndex={-1}` lets a heading receive programmatic focus without adding it to the normal Tab sequence. |
| Navigation and dialogs | Keep the mobile menu's named dialog, initial focus, focus containment, Escape, and focus return. Reuse Headless UI for modal behavior. Ordinary navigation menus are links, not ARIA application menus. |
| Ratings and forms | Reuse the shared review form and native rating radio group. Keep labels, legend, keyboard arrows, validation, Cancel behavior, and focus after save/edit. Give non-submit buttons an explicit button type. |
| Toggles and tabs | Use `aria-pressed` for likes/saved items and `aria-current="page"` for pagination. A toggle's stable accessible name describes its function; pressed state describes selection. Preserve tabs' roving focus, arrow/Home/End keys, Enter/Space activation, and associated panels. |
| Shared state and pending work | Keep desktop/mobile saved-item controls synchronized through the existing Zustand wishlist store and `useWishlistState`. Reuse `useAsyncAction` where appropriate. Preserve synchronous duplicate-request guards and stale-response protection. `aria-disabled` alone does not block activation: guard the handler. |
| Feedback | Reuse `ActionFeedback` and `NotificationContainer`. Announce each result once. Essential errors remain available until dismissed, retried, or their context is left. Do not dismiss another action's error when showing a success toast. Do not report success before confirmation. |
| Drafts and recovery | Keep drafts on failed saves, including session/network failures. Preserve failed-review revalidation guards in `routes.ts`. Keep the sign-in return destination through failed attempts. Page retries reload data without replaying a form submission; distinguish genuine 404s from other failures. Do not promise draft persistence across navigation/reload unless implemented. |
| Focus after async changes | Preserve focus when the user moves elsewhere while waiting. If a focused control disappears, provide a useful destination. Keep `ErrorPage`/`RootErrorPage` recovery titles, error focus, and successful same-URL retry focus. Root recovery must not assume auth data exists. |

## Check the changed UI

Use the linked W3C guidance for exact applicability and exceptions. These checks complement the existing patterns; they are not an exhaustive substitute for WCAG.

- **Names and structure:** use meaningful landmarks, headings and lists; associate labels with fields; give icon controls and image links names describing their purpose. Keep the visible label in the accessible name. Give informative images useful alternatives and decorative images empty alternatives. Identify known language changes where applicable.
- **Keyboard and focus:** make all actions operable without a pointer, avoid positive tab indices, and keep focus order meaningful. Preserve a visible focus indicator and check that the sticky header, dialogs and notifications do not fully hide the focused control. Do not move focus merely because an input changes. For custom widgets, follow the relevant [ARIA APG pattern](https://www.w3.org/WAI/ARIA/apg/patterns/); adding a role does not implement its keyboard behavior.
- **Forms and authentication:** associate errors and instructions with fields, expose invalid state, explain corrections, and focus the first invalid field when appropriate. Keep entered values through correctable failures. Make required format/size/password constraints visible before submission. Retain autocomplete purposes, password-manager support and paste; avoid authentication that relies on unsupported memory or puzzle tasks. See [labels/instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) and [accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html).
- **Feedback:** expose loading/outcome messages through appropriate status/alert semantics without stealing focus or creating duplicate announcements. Keep essential timed information available through a persistent state or an accessible timing/recovery mechanism. See [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).
- **Text contrast:** measure rendered foreground/background colors, including hover, selected, error and focus states. Normal text needs at least 4.5:1; large text needs 3:1 (at least 24 CSS px regular or approximately 18.67 CSS px bold). Use the exact ratios without rounding up. See [text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
- **Controls and selection:** necessary authored control boundaries, graphics and state indicators need 3:1 against adjacent colors, subject to the criterion's exceptions. Do not rely only on hue to convey information. A measured light/dark difference of at least 3:1 can provide an additional distinction; do not assume a different Tailwind color name is sufficient. See [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) and [use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).
- **Reflow and text:** fit ordinary vertical pages at 320 CSS px without page-level horizontal scrolling, except content requiring a two-dimensional layout. Test real 400% zoom at a 1280-pixel desktop viewport and text enlargement to 200%. Let long titles, names, reviews and filter chips wrap; avoid fixed heights that clip text. A carousel may scroll, but each panel must fit its available area. See [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).
- **Text spacing:** avoid loss of content/function when users apply line height 1.5, paragraph spacing 2em, letter spacing 0.12em and word spacing 0.16em. These are user overrides to support, not required default styling. See [text spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).
- **Pointer access:** provide alternatives to dragging or complex gestures. For AA target size, aim for at least 24 by 24 CSS px or a documented applicable exception such as sufficient spacing; do not claim that any gap makes a small target pass. The 44-pixel enhanced target criterion is AAA. See [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).
- **Conditional features:** when adding audio/video, charts, animation, hover/focus popovers, time limits, motion activation or shortcuts, evaluate their specific criteria. Provide media alternatives/captions where required, keyboard equivalents, appropriate dismissal and timing controls. Respect reduced-motion preferences as a useful design practice. Do not mark an untested feature not applicable.

## Validate and report

- Run the smallest relevant existing checks from `client/`: `npm run lint`, `npm run typecheck`, `npm run test:run`, and `npm run build` as appropriate. UI/interaction changes should use the relevant Playwright cases in `tests/accessibility/`; run `npm run test:a11y` when shared behavior changes.
- The browser suite starts its own client on 127.0.0.1:5174 and intercepts API/images with synthetic data. Keep that port free. Install Chromium with `npx playwright install chromium` when needed. Passing mocked tests does not verify the real API, OAuth or deployed build.
- `tests/accessibility/scan.ts` directly requires zero observed accessibility violations. Do not skip a check, weaken assertions, or introduce accepted-violation snapshots to make a change pass. Fix the issue or report the unresolved result. Keep unexpected-request and browser-error guards effective.
- Exercise the changed journey with Tab/Shift+Tab, Enter/Space, arrows and Escape where relevant. Include loading, success, failure, retry and Back/Forward for affected flows. Check narrow screens, long content, spacing overrides, zoom and focus visibility. For a meaningful accessibility sign-off, use an actual screen reader; distinguish browser emulation from native zoom or assistive-technology testing.
- Add focused regression coverage when behavior changes justify it. Do not introduce a new testing framework or test unrelated pages merely because this skill is active. Keep previews, traces and reports in ignored output directories; remove temporary helpers when done. Preserve maintained specs and fixtures.
- Report what changed, what was actually verified, and any remaining barriers. A passing axe scan or unit suite is not proof of whole-client AA conformance. Do not claim screen-reader, production, native-zoom or authentication checks that were not performed.

The [WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/) is the normative reference; [Understanding documents](https://www.w3.org/WAI/WCAG22/Understanding/) and APG explain implementation. Evaluate all applicable A/AA criteria; do not impose AAA criteria such as 2.4.13 as mandatory AA. WCAG 2.2 removed 4.1.1, but markup still must preserve correct semantics and behavior. Full conformance concerns complete pages and processes, including outstanding messaging issues.
